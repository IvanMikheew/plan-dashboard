## 1. Суть и контекст

Дашборд Авито-статистики: пароль → расшифровка `data/avito.enc` (WebCrypto PBKDF2/AES-GCM) →
KPI-плашки, график (canvas), таблица по дням + слой ручных значений (localStorage).
Текущие проблемы: подписи «за 7 дней» фактически описывают весь период (например, 1 967
показов вместо ~888 за 7 дней), дельты «к прошлой неделе» считаются по индексам строк, а не
по календарным дням (сдвигаются при пропусках дат); фильтрации нет; таблица растёт
неограниченно (год = 365 строк).

**Жёсткие ограничения (не нарушать):**
- Крипто-контракт `data/*.enc` ↔ `tools/crypt.js` ↔ страницы — **не меняется** (ADR-0005):
  base64(salt 16Б ‖ iv 12Б ‖ ct+tag), PBKDF2-HMAC-SHA256, 200 000 итераций, AES-256-GCM,
  сессия `plan_pw_v1`.
- Формат расшифрованного JSON (`updated`, `rows[]`, `edits[]`) — не меняется.
- Ручной слой: localStorage, ключ **`avito_manual_v1`** (не переименовывать — потеря данных),
  формат `{cells, adds[{bd, sd, q, t}]}` — не меняется.
- Один HTML-файл, без внешних фреймворков и сборки (GitHub Pages). Всё в `avito.html`.
- Правило дат сохраняется: конверсия «Контакт → запись» — по дате брони (bd); строка
  таблицы — по дате сеанса (sd), иначе брони.

## 2. Пользователь и сценарии

Владелец (массажная практика) смотрит дашборд с телефона/ПК: «как идут показы и записи»,
сравнивает неделю к неделе, правит «Записи новые/старые» руками, добавляет записи.
Сценарии v2: (а) честные 7-дневные цифры и дельты; (б) смотрю за 7 дней / месяц / свой
период; (в) листаю историю по дням по страницам.

## 3. Модель окон и агрегатов (общая для всех требований)

- **Якорь (последний полный день):** `anchor = min(последняя дата в данных, сегодня − 1 день)`.
- **Окно «7 дней»:** `[anchor−6 … anchor]` — 7 последних полных календарных дней.
- **Окно сравнения («прошлая неделя»):** `[anchor−13 … anchor−7]`.
- Все окна — **по календарным датам**, не по индексам строк: день без строки = вклад 0/`null`,
  пропуски дат не сдвигают границы.
- Агрегаты: суммы (`sum`) и доли (`rate = Σчислитель/Σзнаменатель`) — как сейчас, но над
  строками окна. Для долей дельта — относительная, в % (семантика не меняется).

## 4. Требования

### R1. Баг-фикс: честные «за 7 дней» и дельты (обязательно)

- KPI-плашка:
  1. **Значение** = агрегат за **активный период фильтра** (см. R2).
  2. **Метка периода** под значением: «за 7 дней» / «за 30 дней» / «за всё время (N дн.)» /
     «ДД.ММ–ДД.ММ» для произвольного диапазона.
  3. **7-дневная строка** (где есть данные): «за 7 дней: **X** · к прошлой нед. **±Y%**»,
     где X — агрегат за окно «7 дней», Y — дельта X к окну сравнения.
     Если активный период — само окно «7 дней», X не дублируется: «к прошлой нед. ±Y%».
     Нет окна сравнения (мало данных) — только «за 7 дней: X»; нет данных вовсе — «нет данных».
- Пример приёмки: данные, где 7 последних полных дней = 888 показов, весь период = 1 967.
  Под «Всё время»: значение 1 967, метка «за всё время (N дн.)», строка «за 7 дней: 888 ·
  к прошлой нед. …». Под «7 дней»: значение 888. Сегодня плашка врёт (1 967 под «за 7 дней»).

### R2. Фильтры периода (обязательно)

- Пресеты: **«Всё время»** (по умолчанию, текущее поведение), **«7 дней»**, **«Месяц»**
  (= последние 30 полных дней `[anchor−29 … anchor]`), **«Период…»** — произвольный
  диапазон «от–до» (два поля дат + «Применить»).
- Под фильтром — **все блоки**: KPI-плашки, график, таблица. Тренд — по активному периоду.
- Данные — только из уже расшифрованного массива в памяти: без повторных fetch/decrypt.
- Валидация произвольного диапазона: `от ≤ до`; значения ограничиваются диапазоном данных;
  пустое пересечение → «Нет данных за период» (как сейчас), остальные блоки не ломаются.
- Смена фильтра → сброс пагинации на страницу 1 (см. R3).
- Форма «+ Запись» и «Сбросить ручные значения» — глобальные, фильтром не управляются.

### R3. Пагинация таблицы (обязательно)

- **31 строка на страницу**; больше 31 строки в отфильтрованной таблице → новая страница.
- Листание «← Назад / Вперёд →» + счётчик «Стр. X из Y». Порядок строк — как сейчас,
  новые сверху (убывание даты): стр. 1 = самые новые 31 строка; «Назад» = старее.
- Редактирование ячеек «Записи новые/старые» работает на любой странице; правка обновляет
  строку и KPI **без смены страницы**.

### R4. Масштабируемость и структура (обязательно)

- **Рост данных** (год = 365 строк, дальше годы): агрегаты O(n) по строкам окна, DOM
  таблицы ограничен 31 строкой, график — см. R4.3; всё считается из памяти при смене фильтра
  (365–2000 строк — это доли мс, отдельных оптимизаций не требуется).
- **Ручные значения** (localStorage → будущая CRM/MySQL): слой хранения изолирован в один
  модуль-«шов» `ManualStore` (load/save/add/edit/clear) с текущей реализацией на
  localStorage; схема `adds` уже хранит **обе даты** (bd — брони, sd — сеанса) — не терять.
  Реализацию на БД сейчас НЕ строить (YAGNI) — только интерфейс.
- **Производительность на телефоне:** перерисовка графика при ресайзе — с debounce (~150 мс),
  не на каждый тик ResizeObserver; повторный рендер KPI при правке ячейки — точечный
  (обновление значения/подписи), без полного `render()`.
- **Крипто-контракт не ломается** (см. §1). Переезд на Reg.ru (PHP) готовится швами:
  загрузка данных — модуль `DataLoader.load() → {updated, rows, edits}` (сейчас —
  расшифровка `.enc`; будущее — ответ PHP/MySQL, замена одного модуля);
  `ManualStore` — второй шов (будущее — REST). Онлайн-запись в v2 не строится.
- **Переиспользуемость:** фильтр периода (`PeriodFilter`) и пагинация (`Pager`) —
  отдельные модули с единым интерфейсом (состояние → рендер → события), без копипаста
  логики в KPI/график/таблицу; общие селекторы (`filterRows`, `windowRows`, `aggregate`) —
  чистые функции без DOM.

### R5. Блок «Успеваемость к цели» (добавлено 2026-11-26)

- **Цель владельца:** +475 показов за 2 недели (нужный темп ≈ 237,5 показов/нед; сейчас
  ≈103/нед — не успеваем). Конфиг цели — константами в одном месте
  (`GOAL = {views: 475, days: 14}`), правка цели из UI — вне scope.
- **Блок показывает одним взглядом:** (а) текущий темп — показов/нед; (б) нужный темп;
  (в) прогресс-бар «накоплено X из Y»; (г) прогноз «при текущем темпе через 2 недели
  будет N»; (д) вердикт-индикатор: «Успеваем» (зелёный) / «Не успеваем» (красный).
- **Расположение:** верхний блок контента — первым, выше KPI-плашек.
- **Расчёт:** по календарным селекторам (ADR-0001), блок подчиняется фильтру периода:
  окно расчёта = активный период фильтра; цель окна масштабируется по длине
  (475 × дни_окна/14); «Всё время» = окно цели (последние 14 полных дней). Темп =
  Σпросмотров_окна × 7/длина_окна (показов/нед); прогноз = темп × 2 (всегда «за 2 недели»
  к цели 475); вердикт: прогноз ≥ 475 → «Успеваем», иначе «Не успеваем». Семантика
  нормировки и спец-случай «Всё время» — ADR-0006.
- **Края:** <2 дней данных в окне → значения «—», вердикт серый «нет данных»;
  переполнение прогресс-бара → 100% + фактическое число.

## 5. Данные и форматы (см. §1 — всё неизменно)

Расшифрованный JSON: `{updated, rows:[{date, item, impressions, views, contacts, bookings,
bookingsOld, bookingsNew, source}], edits:[даты]}`; `bookings*` = `null` → данных нет.
Ручной слой: `avito_manual_v1` = `{cells:{дата:{new,old}}, adds:[{bd,sd,q,t}]}`.

## 6. Критерии успеха (приёмка версии целиком)

1. Пример R1 про 888/1 967 проходит; дельты не сдвигаются при пропусках дат (проверка на
   наборе с пропусками: расчёт окон сверяется вручную с суммами по календарю).
2. Все пресеты и произвольный диапазон обновляют KPI + график + таблицу без повторной
   расшифровки; «Нет данных за период» при пустом пересечении.
3. 32 строки → 2 страницы (31+1), листание и счётчик работают; смена фильтра → стр. 1.
4. График отображает диапазон фильтра; при >90 дней — недельная агрегация (ADR-0004).
5. Крипто-контракт, форматы `.enc`/JSON/`avito_manual_v1` — байт-в-байт неизменны
   (регрессионный чек-лист IMPLEMENTATION.md).
6. Страница работает на GitHub Pages без сборки и внешних зависимостей, на телефоне
   (resize-дебаунс, таблица 31 строка).
7. Блок «Успеваемость к цели» (R5): при темпе 103/нед — прогноз 206 и красный «Не
   успеваем»; смена фильтра пересчитывает блок; вердикт и прогресс совпадают с ручным
   расчётом по календарным датам.
