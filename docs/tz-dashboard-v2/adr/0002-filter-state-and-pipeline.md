# 0002. Единое состояние фильтра `state.range` и один пайплайн `applyRange()`

- **Статус:** принято
- **Дата:** 2026-11-26
- **Контекст:** фильтры «всё время / 7 дней / месяц / произвольный диапазон» должны
  управлять KPI, графиком и таблицей одновременно; данные — только из уже расшифрованного
  массива в памяти. Без единого состояния логика фильтрации расползётся по трём блокам
  (копипаста — прямо запрещена требованием владельца). Данные растут до 365+ строк.
- **Варианты:**
  1. **`state = {range:{from,to}, page}` + `applyRange()`**: один поток
     `effRows → filterRows → {KPI, chart, table}`; плюсы — один источник истины, блоки
     не знают друг о друге, легко добавлять пресеты; минус — чуть больше «каркаса» в одном
     файле.
  2. Каждый блок фильтрует сам при перерисовке: плюс — кажется проще на старте; минус —
     копипаста, рассинхрон блоков, сложнее чинить баги окон (см. ADR-0001).
  3. URL-параметры фильтра (shareable-ссылки): полезно, но вне требований v2 (YAGNI).
- **Решение:** вариант 1. `range = {from: 'ГГГГ-ММ-ДД'|null, to: ...}`, null = границы данных;
  пресеты выставляют range («Месяц» = скользящие 30 полных дней — SPEC §7.1 открыт);
  произвольный диапазон валидируется (`от ≤ до`, ограничение данными). Дефолт — «Всё время»
  (текущие цифры не прыгают). Смена range сбрасывает страницу пагинации.
- **Последствия:** все перерисовки от фильтра идут только через `applyRange()`; новый блок
  UI под фильтром обязан брать `filterRows(...)`, не свой вариант; URL-параметры — отдельным
  решением позже. Минус: пресеты и custom-диапазон — два разных UI-состояния, нужна явная
  синхронизация выделения кнопок.
- **Связи:** SPECIFICATION.md R2, IMPLEMENTATION.md §1–2; TASKS.md TASK-2 (и сброс
  страницы в TASK-3); файлы: `avito.html` (`state`, `components/PeriodFilter`, `render`).
